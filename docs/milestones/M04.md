# M04 — Profiles and XP ledger

## Objective and boundaries

Implement authenticated self-profile reads/updates, private cursor-paginated XP history, and an internal server-controlled XP award use case. M04 does not implement gameplay verification, client-facing XP writes, character unlock processing, achievements, leaderboards, weekly rewards, administrator workflows, password reset, payments, staking, or cash rewards.

## Assumptions and dependencies

- M03 is approved and merged at `1bb894d`; access authentication checks the live session, account status, and role.
- All seven M02 migrations remain immutable. `0003_progression` already provides profiles, an append-only XP ledger, an idempotency constraint, progression policies, and the required indexes.
- The seeded `progression-v1` policy is effective and not retired: score XP uses floor division by 10 and level uses `1 + floor(total XP / 500)`.
- `displayName` and `bio` are the only client-editable profile fields. Profile mutations use the existing session-bound CSRF mechanism.
- XP awards are invoked only through the internal application service by later trusted server workflows; no browser route exists.

## Acceptance criteria

- `GET /api/v1/players/me` deterministically creates/reads the authenticated player's profile.
- `PATCH /api/v1/players/me` accepts only bounded display fields and requires authentication plus valid CSRF.
- `GET /api/v1/players/me/xp-history` is private, stable, bounded, newest-first, and does not expose database IDs or internal metadata.
- The active database policy controls score-to-XP and total-XP-to-level calculations; missing/retired policy behavior is explicit.
- Internal awards allow only trusted sources, require a valid global idempotency key, append one ledger entry, and update cached total/level atomically.
- Duplicate keys return the original effect for the same payload and conflict on payload/user drift.
- Profile creation and distinct awards remain correct under concurrency; a forced write failure rolls back all progression effects.
- Existing append-only triggers continue rejecting XP update/delete operations.
- M01–M03 regression tests, MariaDB verification, OpenAPI/Postman parsing, quality checks, and MySQL 8.4 CI pass.

## Test matrix

| Area          | Positive evidence                                                   | Negative/integrity evidence                                                                          |
| ------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Profile       | Create/read/update own display fields                               | Unauthenticated, missing CSRF, unknown/protected fields, empty body, and other-player paths rejected |
| Creation race | Concurrent first reads return one profile                           | No duplicate or transient 404                                                                        |
| Policy        | Database policy gives score/XP and 0/499/500/multi-level boundaries | Missing/retired policy blocks creation and awards safely                                             |
| Award         | Trusted source appends ledger and updates cache                     | Unknown/client/adjustment source and malformed keys/amounts rejected                                 |
| Idempotency   | Same key/payload returns original effect                            | Same key with changed payload conflicts                                                              |
| Concurrency   | Distinct concurrent awards preserve exact sum/cache/level           | Deadlocks are retried; no lost update                                                                |
| Transaction   | Ledger and cache commit together                                    | Forced profile-write failure rolls back ledger insert                                                |
| History       | Stable cursor pages only the current player                         | Invalid cursor/limit, other-player path, IDs, and metadata rejected/absent                           |
| Immutability  | Ledger history remains queryable                                    | Existing database triggers reject update/delete                                                      |
| Regression    | Complete Mocha suite and build                                      | Any inherited failure blocks PASS                                                                    |
